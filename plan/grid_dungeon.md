# 格子房间地牢扩展计划

> 状态：后续扩展规划，尚未实施。
>
> 前置依赖：`plan/scene_chain_dungeon.md` 的场景链垂直切片已经验证战斗、奖励、营地与永久成长。本计划在此基础上增加空间探索，不要求恢复六边形地图引擎。
>
> 首版场景链不被本计划阻塞；格子玩法必须先证明其路线规划价值，不能仅因已有网格绘制代码而自动进入 DEMO。

## 1. 目标与核心体验

将场景链扩展为固定格子地图上的房间放置与探索：

- 玩家从固定起点开始，终点位置明确。
- 每次选择可前进方向或相邻空格，从三个候选房间中选择一个放入地图。
- 已放置房间成为实际场景，可以进入并完成战斗、NPC、商店、休息或奖励内容。
- 玩家可以返回已经访问的房间，再次使用仍然有效的商人和设施。
- 穿梭消耗体力；体力不会自动恢复，耗尽则本次冒险失败。
- 门和箱子可能免费打开，也可能消耗秘境金币或通用钥匙。
- 到达终点并完成 Boss 后返回营地，在当前境界上限内提高下一轮秘境层级。

目标不是增加随机性本身，而是形成：

> **房间放置 + 路径规划 + 回访价值 + 体力预算 + 构筑成长。**

## 2. 房间、移动与回访规则

### 房间放置

- 地图使用普通整数坐标和上下左右邻接，不使用六边形坐标。
- 空格被选择后展示三个候选房间，候选内容在展示时生成并保存。
- 选择后房间永久占据该格子；首版不支持删除、替换或旋转已放置房间。
- 房间卡至少显示内容类型、出口方向、门锁和主要风险／奖励，不在选择后才随机改变这些信息。
- 非主路径区域允许出现死路、门锁和低价值房间，但不能破坏主路径的可解保证。

### 移动与回访

- 每次移动到相邻房间消耗 1 点体力，前进与返回同价。
- 移动前显示消耗；体力不足时禁止移动并明确提示。
- 玩家始终可以主动放弃本次冒险，不能被战斗或地图状态永久卡住。
- 回访不消耗除移动外的额外体力，不重新生成房间、敌人、商品或奖励。
- 已击败敌人和已打开箱子不因回访重置，已自动发放的普通战斗奖励不会重复生成或发放。
- 战后搜刮沿用场景链规则：普通战利品展示关闭后，从敌人实际出战卡组随机抽取三张并在当前房间显示 Component；暂时关闭可由敌人重新打开，选择或放弃才完成；所有状态保存在房间实例中，回访和读档不重 roll。
- 商人保留首次生成的商品与库存；营地设施保留使用状态。
- 首版地图只读，实际移动仍通过当前房间的出口或场景选项完成，不另做一套地图点击移动规则。

## 3. 体力、金币、钥匙与门锁

### 体力

- 体力是当局移动预算，不与生命、卡牌费用或世界时间混用。
- 体力不会自动恢复；恢复只能来自明确、有限的内容效果。
- 初始体力应允许到达终点并探索若干支路，不能只够走最短路线。
- 体力耗尽触发失败，按场景链失败规则返回营地，下一轮层级归零。

### 金币与钥匙

- 秘境金币同时服务商店消费和部分门／箱子，形成花费取舍。
- 钥匙是通用道具，不区分颜色、形状或门锁类型。
- 钥匙主要用于可选高价值内容，不用于未保证可获取的主路径硬锁。
- 门锁状态在开启后永久保存，不因回访或读档恢复为锁定。
- 不新增多色钥匙、复杂锁具、运输或独立副职业体系。

## 4. 保证可解的主路径

不采用“随机门向导致整局永远无法到达终点”的规则。失败应来自玩家的资源分配和战斗，而不是不可预知、不可补救的地图结构。

### 预生成 `solutionPath`

每局初始化时预生成一条从起点到终点的路径：

- 只使用上下左右相邻格子；
- 不重复占用格子；
- 不依赖必须付费的门；
- 不依赖尚未保证获得的钥匙、金币或特殊房间；
- 路径数据保存在当局并随存档恢复。

### 主路径房间保证

当玩家点击 `solutionPath` 上的格子时，三个候选房间都必须满足：

- 具有通往相邻前后路径格的入口与出口；
- 这些方向的门可以免费打开；
- 转角房间同时具有两个所需方向；
- 起点和终点只需连接实际相邻的路径格。

如果玩家从非预期方向进入主路径格子，则房间必须连接所有实际相邻的前后路径格，不能只检查一个预设前进方向。

非主路径房间仍可随机门向、门锁和奖励。支路可以断开或产生额外绕路，但不得覆盖已放置主路径房间并破坏原保证。

### 可解性验收

使用多组 seed 自动验证：

- 沿 `solutionPath` 前进必然可以通过免费门到达终点；
- 任意支路放置和回访都不会取消该保证；
- 转角、从反方向进入和读档恢复后的门向一致；
- 主路径不要求未保证提供的资源；
- 暂时断连和可选死路允许存在，永久不可解的终点路径不允许存在。

## 5. 胜负、结算与永久成长

终点房间包含 Boss 或阶段目标。成功后返回营地，带回随身物品，保留同一英雄、永久卡和角色成长，并在当前境界上限内提高下一轮秘境层级。

失败、体力耗尽或主动放弃时：

- 返回营地，下一轮层级归零；
- 保留角色、永久卡库、仓库、装备栏和境界；
- 清空未入库且未装备的随身物品与材料；
- 移除所有 `isDungeonCard` 卡牌；
- 不重新随机创建角色。

胜利与失败都移除地牢卡；默认卡继续只在战斗中虚拟补位。仓库、装备栏和随身物品栏的保留规则与场景链完全一致。

## 6. 数据结构与职责分工

### 6.1 `DungeonRun` 扩展

格子模式继续使用 `game.flags.dungeon` 中的 HTStruct，不建立第二份 Dart 持久真值。新增或按模式使用：

- `mode: grid`；
- `width`、`height`、起点、终点与当前位置；
- 以 `"x,y"` 为键的房间实例表；
- 已探索、已完成、门锁和普通奖励状态；
- 已击败敌人的三个搜刮候选，以及选择／放弃完成状态；
- `solutionPath`；
- 当前体力、秘境金币与通用钥匙；
- 当前三个候选房间及选择状态；
- 当前场景、战斗、自动发奖、搜刮与结算状态。

场景静态内容继续放在 `assets/data/dungeon_scenes.json5`。房间实例保存生成结果，打开地图、回访或读档时不得重 roll。

### 6.2 Dart

负责：

- 主路径与候选房间生成；
- 格子邻接、放置、移动和回访；
- 体力、金币、钥匙与门锁结算；
- 战斗和事件完成后的地图状态更新；
- 失败、Boss、难度推进和场景恢复；
- 地图 UI、交互锁与浮窗。

### 6.3 Hetu 与 JSON5

- Hetu 继续负责 `DungeonRun` 初始化、敌人／商品／奖励和卡牌物品工厂。
- JSON5 负责房间模板、出口形状、门锁、内容引用、权重、图标和本地化。
- 首版不增加格子场景专属 `onEnter`／`onComplete` 脚本回调；简单效果使用受控动作类型与参数。

## 7. 地牢地图场景与 MouseMaze 复用

### 7.1 场景形式

新增固定、只读的 `DungeonMapScene`：

- 探索阶段通过 `engine.pushScene()` 打开，关闭时 `popScene()` 回到原 `DungeonScene`；
- 直接读取 `game.flags.dungeon`，不创建第二份地图状态；
- 打开和关闭不消耗体力、不推进时间、不重新生成房间；
- 战斗、观星、对话、商店和其他模态交互期间遵循现有交互锁，不强行覆盖这些界面；
- 首版只查看，不通过地图点击移动。

### 7.2 可借鉴的 MouseMaze 实现

`lib/scene/mini_game/mouse_maze/mouse_maze.dart` 可参考：

- `_Cell` 的四方向墙壁与访问状态，约 `:241-248`；
- `_Maze` 的格子定位、居中布局和墙壁绘制，约 `:283-401`；
- 起点、终点和当前位置标记；
- BFS 路径检查与通道方向判断，约 `:758-873`。

这些类当前为文件内私有实现，不能直接 import。实施时提取必要的通用网格绘制，或新建更简单的 `DungeonMapView`，不共享小游戏场景本体。

不复用光点拖拽、墙壁碰撞、传送门、定时门、错误次数、小游戏胜负和 DFS 迷宫生成。

## 8. 房间图标与浮窗

### 8.1 首批通用图标

- 普通战斗：剑或交叉兵器；
- 精英：强化兵器或精英徽记；
- Boss：王冠或首领徽记；
- 商人：钱袋；
- 休息／营地：篝火；
- NPC／事件：卷轴或问号；
- 宝箱：箱子；
- 起点与终点：入口、出口或传送门。

门锁使用小型角标或叠加图标表达免费、金币和钥匙，不为每种组合制作独立图片。

### 8.2 状态表现

状态由房间实例派生，不重复生成图片：

- 当前位置：高亮描边或外圈；
- 已完成：降低饱和度并显示完成标记；
- 已探索：显示实际房间图标；
- 已放置但未进入：只显示通用轮廓及选择时已公开的信息；
- 未探索格子：不显示房间内容。

### 8.3 浮窗内容

已探索房间图标使用现有 Hover 机制显示：

- 房间名称、类型与描述；
- 敌人是否已击败；
- 商人是否仍有商品；
- 普通战斗奖励是否已自动发放、搜刮是否完成、宝箱是否已开启；
- 各出口的免费／金币／钥匙状态；
- 回访后仍可使用的功能。

浮窗直接读取房间实例与本地化数据，不另存一份地图专用描述。

### 8.4 美术制作

- 图标采用统一视角、描边、配色和单一象征物，无文字。
- 按地图实际显示尺寸检查可辨性，而不是只看原图。
- 优先通过同一风格提示词生成一组通用图标，再统一缩放和筛选。
- 场景插画与地图图标分开管理，地图图标不注册为战斗状态图标或卡牌插画。
- 先以占位图标验证地图和浮窗，再制作正式资源。

## 9. 分阶段实施顺序

### 阶段 1：网格状态与可解性

- 扩展 `DungeonRun` 的格子数据与初始化。
- 实现固定地图、主路径和房间出口数据。
- 先完成多 seed 可解性测试，不制作地图美术。

### 阶段 2：放置、移动与体力

- 实现三选一放置、相邻移动、回访和体力消耗。
- 打通普通战斗、事件、精英和终点 Boss。
- 验证失败与永久成长规则和场景链一致。

### 阶段 3：门锁与回访价值

- 加入免费、金币和通用钥匙门锁。
- 加入箱子、商人库存与设施回访状态。
- 防止回访刷奖励和读档重 roll。

### 阶段 4：只读地图与图标浮窗

- 新建 `DungeonMapScene` 与 `DungeonMapView`。
- 实现房间、出口、当前位置、起点终点和资源显示。
- 接入通用图标、状态样式和房间浮窗。
- 验证打开地图不改变任何当局状态。

### 阶段 5：整合与评估

- 完成场景边界保存、读档与根场景恢复。
- 对比场景链与格子模式的路线选择、战斗节奏和体力压力。
- 若格子模式没有明显提高探索决策价值，则保留场景链，不继续增加地图规则。

## 10. 验收与范围边界

### 真实流程

至少验证：

1. 放置战斗房并胜利 → 返回地图 → 选择支路 → 消耗体力 → 回访商人。
2. 免费、金币与钥匙门分别开启并保存状态。
3. 沿主路径到达终点并击败 Boss → 返回营地并保留随身物品 → 下一轮层级提高但不超过境界上限。
4. 体力耗尽、战斗失败与主动放弃 → 返回营地 → 未保护随身物品与地牢卡移除，仓库、装备栏和永久卡保留。
5. 地图打开／关闭、房间回访和场景边界读档后，门向、商品、普通奖励、搜刮候选与完成状态、体力和 RNG 状态一致。

### 标准验证命令

按实际改动运行：

```bash
python build.py
flutter analyze
dart run utils/data_validate/game_data_validate.dart
flutter test
```

### 不在本计划内

- 六边形地图、寻路、地图光照和六边形资源体系；
- 多色钥匙、复杂锁具与随机必死主路；
- 地图点击移动与房间旋转的首版扩展；
- 大地图解密、复杂墙体拼接和任意形状房间；
- 独立地牢脚本系统、世界时间和 NPC 日程；
- 为每个具体房间制作独立地图图标。

本计划只有在“放置、回访和体力预算确实增强构筑体验”时才继续扩大内容，否则停留为可裁剪实验。
