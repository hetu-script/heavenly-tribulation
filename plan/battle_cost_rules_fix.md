# 动态卡牌费用、Samsara 渲染与敌方支付修复计划

状态：已实施并完成代码与数据验证。Samsara 显示沿用现有位置和字号，不处理文字溢出；实际显示效果待用户运行确认。

## 1. 目标

- 焚天烈焰取消固定基础费用，消耗当前全部灵气，卡面显示 `X`。
- 万法归宗要求至少 10 点灵气，消耗当前全部灵气，卡面显示 `10+X`。
- 动态费用统一豁免减费，包括组牌减费、观星减费、抽牌费用置零及临时减费。
- Samsara 支持动态费用显示。
- 敌方依据实际可支付手牌出牌，元气耗尽后仍能使用有色牌或免费牌。

前版对焚天烈焰基础费用的判断有误。本计划以用户修正后的设计为准。

## 2. 数据格式与运行时格式

采用费用条目上的 `isDynamic`，本次不再新增卡牌级 `isCostReductionForbidden`。

```json5
// 焚天烈焰：无固定门槛，消耗当前全部灵气
coloredCost: { spell: { base: 0, isDynamic: true } },

// 万法归宗：至少 10 灵气，支付全部灵气
coloredCost: { spell: { base: 10, isDynamic: true } },
isWildcardCostForbidden: true,
```

`base + rankIncrement × rank` 求得最低支付门槛。`rankIncrement` 可省略，默认 0。`isDynamic` 缺省 false；普通费用继续按原规则处理。

运行时采用两种条目：普通费用仍为整数，动态费用保留 `{base: 求值后的整数, isDynamic: true}`：

```text
{spell: 3}
{spell: {base: 0, isDynamic: true}}
{spell: {base: 10, isDynamic: true}}
```

`updateCardCost` 保留 base 为 0 的动态条目，避免被当作免费卡过滤；`originalColoredCost` 深拷贝条目，避免当前费用修改连带改变基线。

Samsara 接收已求值的运行时条目，只负责显示 base 和 X，不负责境界公式或战斗资源规则。

## 3. 支付语义

### 3.1 动态消耗

动态费用在 `_payCardCost` 支付阶段结算：达到最低门槛后，支付该颜色对应资源的全部当前存量，并把实际扣除量写入 `cardFlags['paidCost']`。

`10+X` 中 X 是超过最低门槛的剩余部分。例如 12 点灵气支付万法归宗，实际扣除 12，X 为 2；并非在 12 之外另收 10。

X 只指对应颜色的资源。太极之气不因“耗尽”而被一并消耗。最低门槛的太极抵扣仍由 `isWildcardCostForbidden` 控制：万法归宗保留禁止抵扣；焚天烈焰最低门槛为 0，自然无需抵扣。若未来其他动态牌允许抵扣，只用太极补最低门槛的缺口。

推荐允许 X = 0：零灵气时可打出焚天烈焰，但伤害效果不触发，不调用要求正伤害的 `takeDamage`。如果设计需要“至少 1 灵气”，应明确最低门槛，不能把 X 隐式当作 1。

### 3.2 动态费用修改

- 减费与置零：跳过动态条目，不改变其 base 或 isDynamic。
- 加费：允许提高最低门槛，如 `X → 1+X`、`10+X → 11+X`。实际支付仍为全部对应资源；加费提高能否出牌的门槛。
- 临时加费到期还原：恢复 base，保留动态标记。
- 对整张牌置零时：保留动态条目；若未来存在混费，普通条目仍可按原规则置零。

费用调整代码统一区分整数与动态条目，不直接对对象做加减运算。Dart 侧提供小型通用解析/调整辅助函数；Hetu 调息脚本读取相同条目约定。

本次只迁移焚天烈焰和万法归宗。其他元气转化、护甲转化卡牌继续按现有设计处理，后续可用此格式显式迁移。

### 3.3 脚本消费实际支付量

两张牌统一绑定到通用内容脚本，例如 `attack_by_paid_resource`：

1. 从 `self.cardFlags['paidCost'][affix.resourceId]` 读取实际支付的对应气量。
2. 支付量为 0 时不造成伤害。
3. 伤害基础值 = 实际支付量 × affix.value[0]。

焚天烈焰使用火伤，万法归宗使用雷伤，通过数据字段决定。删除被替代且无其他引用的旧脚本，避免仍按“支付后耗尽剩余气”重复扣除或漏算。

支付发生在 using_card、额外词条和主词条之前。动态牌因此消耗开始结算时可用的气；结算过程中后来获得的气留给后续卡牌。退款词条继续读取实际 paidCost，可按其规则返还。

## 4. 支付检查、提示与队列预占

当前 `_cardCostColored` 只接受数值，直接保留对象后会静默漏掉动态费用，必须同步调整：

1. **费用解析**：读出颜色、最低门槛、动态标记，供支付检查与支付共用。
2. **支付计算**：抽取共用的支付明细计算，计算元气、本色气、太极缺口及动态耗尽量，资源不足时不扣除任何资源。每张牌先使用本色气，再按该牌的抵扣规则补太极缺口；队列严格按出牌顺序模拟，不为后续牌提前保留本色气。
3. **入队预占**：按队列顺序在资源余额副本上模拟费用支付；动态牌预占执行到该位置时的全部本色气，不只预占最低门槛。此处只模拟支付，不提前运行卡牌获得资源等内容效果。
4. **实际出牌**：重新根据当时余额计算并支付，继续保留资源不足时退回手牌的处理。
5. **手牌置灰与缺资源提示**：与支付计算共用最低门槛规则，提示实际缺少的资源；X = 0 的焚天烈焰不会仅因灵气为 0 置灰。
6. **伤害预测入口**：适配新费用解析的数据形状。当前描述里的 `{0}` 是“每点气伤害”，继续显示该单位伤害预测；本次不把它换成总伤害，避免描述变成错误的“每点气造成总伤害”。

队列示例：12 灵气先入队一张 2 费牌，再入队万法归宗，预占分别为 2 与剩余 10。若先入队万法归宗，则其预占全部 12，后续需要本色灵气的牌不可再靠同一笔存量入队。

## 6. Samsara 卡牌渲染

修改本地依赖 `../samsara-engine/lib/cardgame/custom_card.dart` 的 `_coloredCostEntries` 与 render。

- 解析整数和 `{base, isDynamic}` 两种运行时费用，兼容 Map 与 HTStruct。
- 动态 base 为 0 显示 `X`，大于 0 显示 `N+X`；保留零基础动态条目。
- 与 originalColoredCost 比较最低门槛，延续增加标红、减少标黄的规则。
- compact 模式沿用现有资源图标、文字位置、字号和绘制方式，直接显示 `X` / `N+X`。保持渲染代码简洁。
- pips 模式的动态条目以一个图标叠加 `X` / `N+X` 表示；普通整数条目继续按原方式重复图标。
- 本次不增加文字测量、自动缩放或防溢出逻辑，不调整游戏侧费用显示区域。具体显示效果由用户实际运行后评估，再决定后续布局修改。

已读引擎的 AGENTS.md。引擎代码只承担通用显示，不加入悟道卡牌或游戏资源 id。

## 7. 敌方出牌循环

移除 \_startTurn 敌方循环中的 `currentCharacter.energy > 0` 条件。

每轮用更新后的通用 \_canPayCardCost 计算可支付候选，无候选即结束；选牌后用同一支付计算执行 \_payCardCost。保留重开、胜负、手牌非空及支付失败退回处理。每张牌结算后重新计算余额，覆盖动态耗尽、退款、产气和抽牌。

## 8. 数据、契约和本地化同步

- assets/data/cards.json5：两张牌的动态费用、脚本绑定和 resourceId。
- scripts/main/cardgame/card.ht：动态费用求值与基线深拷贝；修改触及的费用注释同步更新。
- scripts/main/cardgame/card_script.ht：通用实际支付量伤害脚本、调息费用适配。
- lib/scene/battle/battle.dart、character.dart：费用解析、支付、修正、提示、队列和敌方循环。
- lib/data/game.dart：数据加载校验接受省略 rankIncrement 的动态条目，动态费用不套用普通流派卡的 rank 费用惯例。
- utils/data_validate/game_data_validate.dart：校验 isDynamic 的布尔类型、base 非负、rankIncrement 可选数值；同步新脚本必需 resourceId 的契约，并校验 isWildcardCostForbidden 类型。
- assets/locale/zh/rpg/battlecard.json：明确焚天烈焰消耗全部当前灵气，万法归宗至少 10 灵气且不参与减费、不允许太极抵扣。
- docs/docs/mod/battle/card/readme.md、docs/docs/mod/battle/readme.md：数据与运行时条目、动态支付顺序、减费豁免、加费规则及 paidCost 说明。
- plan/skill_tree/spellcraft.md、plan/battle_system_overview.md：同步两张牌的最终费用与实现依据。

实现前重新检查两个仓库工作区，保留用户已有修复。当前沙箱写入范围仅包含游戏目录；引擎写入和检查若被沙箱拦截，届时通过工具申请相应访问。
